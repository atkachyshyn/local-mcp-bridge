# Independent architecture peer review — Local MCP Bridge v0.9.2 stabilization

**Reviewed:** `main` @ `1322d7b` (working tree) + `V0.9.2 Stabilization Architecture Proposal`
**Revision 2.** Revision 1 reviewed the proposal's summary only; the document was
not in the repository. Revision 1's verdict was REWORK BEFORE IMPLEMENTATION.

# Verdict: APPROVED WITH REQUIRED CHANGES

---

## 0. What changed from revision 1, and why

Revision 1 raised seven objections to the proposal. The full document answers
four of them outright, and I withdraw those:

| Rev-1 objection | Status against the real document |
|---|---|
| P1 `registered` collides with existence-implies-ambiguous journal semantics | **Withdrawn.** §8 defines an explicit `registered -> executing -> completed` lifecycle and states the four recovery cases directly. The distinction is a status field, not file existence. |
| P2 mutation ambiguity not addressed | **Withdrawn.** §10 is correct and complete — dispatched WRITE/DESTRUCTIVE with anything short of an unambiguous success is `unknown`, `isError=true` included, and no transparent mutating retry after session loss. |
| P4 "submission acknowledgement" has no source | **Withdrawn.** §14 names it: a new user message containing the exact canonical result, with composer-clear as secondary evidence. |
| P5 "semantic" composer comparison weakens it | **Largely withdrawn.** §14 puts the strictness in `parsePureResultEnvelope` (no prefix/suffix human text, schema-checked) and only then compares semantically. That is the right split, and better than revision 1's byte-normalized suggestion: contenteditable mangles whitespace, so byte comparison would produce false negatives. |

Three stand, in reduced form: the conversation identifier is still unnamed
(§2.1), the `session` lease scope is still ambiguous (§2.6), and `recent_tasks`
truncation still needs a display-only declaration (§2.7).

The proposal is sound in its boundaries and its priorities. Everything below is
clause-level tightening, not redirection. **The single largest remaining risk is
that §6's enable-baseline rule is self-contradictory and, in one of its two
readings, reintroduces the exact stale-task bug the release exists to fix.**

All of revision 1's findings against the *implementation* stand unchanged and
are not restated here; §1 of the previous revision is preserved as
`v0.9.2-implementation-findings.md` in intent. The proposal's §2 correctly
identifies the committed token and the red test baseline, and my measurements
agree with both.

## 1. Required changes to the proposal

### R1 — §6: the enable baseline is stated two incompatible ways, and one of them is broken

§6 says both:

> "Enabling records the currently visible provider user/assistant turn IDs as a baseline."

and

> "Local MCP starts on the next genuine human turn."

These are different rules. **The first is unsafe.** "Currently visible" is
precisely the quantity ChatGPT virtualization destroys — the release's founding
defect. A user who enables while scrolled up in a long conversation records a
baseline at an old turn, and every task after that old turn becomes eligible.
That is stale-task execution reintroduced through the front door, and §20's
"enable on existing chat does not execute historical task" would pass in
testing (short chats, scrolled to bottom) while failing in use.

Enumerating all existing turn IDs is not available either, for the same reason.

**Required:** define the baseline as *observation*, not *enumeration*. A turn is
in-scope only if the coordinator watched it appear while enabled — a turn ID
absent from the daemon's `last_user_turn_id` lineage **and** first observed
after the `enable` call's recorded timestamp/sequence. Delete the "currently
visible ... baseline" sentence. Add to §5 an `enabled_at_sequence` (or
`baseline_established: false` until the first observed new human turn) so the
rule is expressible in daemon state rather than in browser memory.

Corresponding §20 test must be strengthened: *enable while scrolled to the top
of a conversation containing prior tasks, then scroll down — nothing executes.*

### R2 — §7: `register_task` loses idempotency, contradicting §20's reload determinism

§7: "requires current phase `awaiting_assistant`".

Today `daemon.py:388` returns `{registration: "known", task: existing}` for an
already-registered task **before** the phase/checkpoint gate. Registration is
idempotent now. Taken literally, §7 is a regression: reload during
`task_registered` leaves the persisted phase at `task_registered`, the
coordinator rediscovers the same assistant turn, calls `register_task`, and is
refused — with no stated path back. §20 requires "reload at every phase is
deterministic," and the §7 contract as written cannot satisfy it.

**Required:** specify re-attach explicitly. `register_task` must be idempotent
on `(conversation_id, assistant_turn_id, task_digest)`:

- same turn, same digest, task already registered → return the existing
  registration handle, whatever the phase. Not an error.
- same turn, **different** digest → fail closed (assistant message edited).
- different turn while phase is `task_registered`/`executing` → fail closed;
  this is the countermand case and belongs to the human-turn path, not here.

The phase gate applies to *creating* a registration, never to *resolving* one.

### R3 — §4: name the identifier, or the section is unimplementable

§4 defers to "the actual ChatGPT/project URL shapes observed in manual release
tests." A security-relevant state key cannot be specified by future observation.

**Required:** name it normatively. The `/c/<uuid>` path segment is the correct
choice — a stable, publicly visible route parameter, not a private API,
surviving reload and multi-tab. Specify:

- canonical id = the validated UUID from `/c/<uuid>`, hashed SHA-256 as §4 says;
- every other route shape (`/`, `/g/g-*/project`, anything without a
  conversation UUID) is **provisional and per-tab**, keyed
  `provisional:<tabId>:<random>`;
- provisional state carries no approval leases and no `enabled` flag that
  survives the tab;
- `bind_conversation` migrates provisional → canonical exactly once and
  **refuses if the canonical key already exists**.

This last clause is load-bearing. Without it, two tabs that each start at `/`
and land on the same conversation both attempt migration.

Measured today for context — the collision is not hypothetical:

```
'/'                      -> chat-2a0c975e
'/?model=x'  (pathname /)-> chat-2a0c975e   <-- same bucket
```

Because `enabled` lives in that bucket, enabling once in any new chat currently
enables every future new chat in every tab. §4 fixes this only if provisional
keys are per-tab, which is why that clause must be normative rather than implied.

### R4 — Multi-tab is in the test matrix with no mechanism to make it pass

§20 requires "two tabs on one conversation cannot double execute." §13
serializes the coordinator **within one tab**. Two tabs are two coordinators
against one daemon conversation state. The daemon's per-conversation lock
serializes individual writes; it does not prevent both tabs from driving the
state machine.

Concretely: both tabs observe the same assistant turn, both register (idempotent
after R2, fine), both preview and approve, one executes and the journal blocks
the second (fine) — and then **both insert and submit the result, and both
report submission**. §11 increments the checkpoint window on submission
acknowledgement. Two acknowledgements, two increments, one task.

§5 already carries `revision: 42` but the proposal never says what it is for.

**Required, and one mechanism closes both gaps:** make `revision` normative
compare-and-swap. Every mutating conversation call carries `expected_revision`;
the daemon rejects on mismatch and returns current state. Then:

- window advancement is idempotent because the losing tab's CAS fails;
- a `submission_ack` must additionally be idempotent on the *provider turn id*
  of the submitted result, so a retry of the same acknowledgement is a no-op
  rather than a second increment;
- add an `owner` field — `{tab_token, expires_at}` — renewed by the active
  coordinator. A tab that is not owner renders read-only and is refused
  `register_task` / `execute`. Do not attempt to merge two event pumps.

### R5 — §10: close the "server-specific contract" escape hatch for this release

§10's rule is correct, then adds:

> "unless a server-specific contract proves no mutation occurred"

and

> "unless explicitly known atomic/no-effect"

There is no mechanism for expressing such a contract, no place to store it, and
§22 forbids new features. An undefined exception to the one genuinely
conservative rule in the document is where that rule quietly erodes.

**Required:** state that **v0.9.2 defines no such contract mechanism and admits
no exceptions.** Everything dispatched that does not return an unambiguous
success is `unknown`, full stop. Note the hook as a post-0.9.2 design question.

On the cost of that conservatism — it is low, and worth saying so in the
document to preempt the pressure to weaken it later: a false `unknown` costs one
acknowledgement click via the existing recovery path; a false `error` costs a
double-applied patch. Pre-dispatch denials (policy, preflight, connection
refused before the request is written) remain ordinary `error`, so the common
failure path is unaffected. Add a §20 test asserting that READ/VERIFY failures
still yield `error`, to guard against over-correction.

### R6 — §17: option 1 is not available, because the thing to be documented is a bug

§17 offers "keep the implementation but explicitly document roots as
explicit/detectable path-argument containment."

The current walker does not do what accurate documentation would have to claim.
`is_path_key` (`daemon.py:951`) recognizes `PATH_KEYS` ∪ `*_path` ∪ `*_dir`; for
every other key name only *absolute*-valued strings are collected
(`:1010-1013`). A tool whose argument is named `file`, `filename`, `target`,
`dest`, `src` or `output` and receives `"../../../../.ssh/id_rsa"` gets **no
root check and no fail-closed** — while `ARCHITECTURE.md:161` and the
`collect_path_arguments` docstring both already claim relative values fail
closed.

Separately, `FREEFORM_TEXT_KEYS` (`:939`) exempts `patch`, `content`, `old`,
`new` from detection entirely — and for a patch-shaped tool the patch header
*is* the write target.

**Required:** §17 must include a minimum fix, not only a documentation choice:

1. any string value that is path-shaped (contains `/`, or starts with `~`/`.`)
   in an unrecognized key fails closed unless it resolves inside a root — the
   `FREEFORM_TEXT_KEYS` exemption stays, but exempt keys make the *operation*
   ineligible for `write`/`destructive` rather than merely skipping the check;
2. or, equivalently, a server exposing a tool with a free-form payload field may
   not be granted `write: true` without a per-tool argument-policy adapter.

Then document. Revision 1 checked the existing prose and it is otherwise honest
— `SECURITY.md:7,34`, `README.md:120`, `ARCHITECTURE.md:138,261` all correctly
disclaim OS sandboxing. The gap is the implementation, not the claim.

### R7 — §15 removes `Run again` without adding a recovery affordance

Deleting `Run again` is right. But §9 explicitly contemplates a task that
completes locally and fails delivery, and after §15 there is no user-reachable
path to that journaled result.

**Required:** add a distinct **`Re-deliver result`** action, enabled only when
`execution_status ∈ {completed, error, unknown}` and `delivery_status ∈ {none,
inserted, failed}`. It replays the stored canonical result into the composer and
never re-enters MCP. This is the user-facing face of journal replay and should
be named as such so it is not confused with re-execution.

### R8 — §16: delete the legacy envelope markers

§16 removes runtime LBP 1.1. It does not mention `protocol.js:2-6`, which still
scans for `<LBP_TASK_V1>` and `<ATLAS_TASK_V1>`. Those envelopes carry
`version: "1.1"` payloads that the same file will now always reject — parsed,
then refused. Dead surface that still consumes every assistant message.

**Required:** delete both legacy entries from `ENVELOPES` in the same change.

### R9 — §12: resolve `session` scope to one thing

§12 says `session` is "current browser-session/conversation scope up to TTL/risk
level"; §20 says "conversation/session scoped." Both leave it undetermined.

**Required:** bind session leases to `(conversation_id, server)` server-side and
remove `session_id` from the lease key. A lease must not survive a conversation
change. Keep the 2-hour TTL and the destructive hard gate as they are — both are
correct today and §12 rightly preserves them.

Minor, same section: when §11 increments the window, evict the superseded
`chain_id + ".w" + N` lease eagerly. `cleanup_approval_state` (`:1118`) evicts
on TTL only, so a superseded window lease currently lingers for up to two hours.
It is unreachable — `chain_id` is random per chain and `window` only increases —
so this is hygiene, not a hole. Worth one line.

### R10 — §5: declare `recent_tasks` display-only

Today `state["tasks"]` is silently truncated at 256 (`daemon.py:1403`). §8
correctly says historical task knowledge must not be deleted on a new chain, and
§7's duplicate-ID rejection is a *journal* lookup. So truncation is fine —
provided the document says so.

**Required:** state that `recent_tasks` is a bounded presentation projection and
that **no staleness, currentness, or duplicate-ID decision may read it.** The
conversation-scoped journal is the only durable authority. Without this line, an
implementer will reasonably use the in-state list for the duplicate check and
reintroduce the collision class at exactly 257 tasks.

## 2. Smaller notes, worth folding in

- **§6, edited prior turns.** ChatGPT permits editing an earlier message. A
  bridge-result turn edited after the fact will differ from the daemon's stored
  result and trigger "fail closed and stop." That is the correct behaviour, but
  it is a usability cliff with no explanation surface. Give it a distinct
  stopped-reason so the sidebar can say *why*.
- **§11, orphaned checkpoint result.** If the user never presses Continue and
  instead types a new prompt, the composer holds the task-12 result plus their
  text; §14's parse correctly classifies it as a genuine human turn and starts a
  new chain. The task-12 result is then journaled `completed` /
  `delivery_status: inserted` forever. R7's `Re-deliver result` covers recovery;
  say so in §11 so the case is visibly handled rather than merely survivable.
- **§14, acknowledgement is still a browser assertion.** The daemon cannot see
  the DOM, so "provider acknowledged submission" is ultimately reported by the
  coordinator. This is fine and worth stating explicitly as an accepted residual
  — and note *why* it is safe: a browser that falsely claims submission advances
  into a window with **no** approval lease (§12), so the failure mode is a
  stalled chain, not unauthorized execution. That is a genuinely good property
  of the design and should be written down rather than rediscovered.
- **§2.1, history rewrite.** Amending the pushed commit is worth doing but does
  not reliably remove the object from a public host (forks, PR refs, caches).
  The proposal already says rotation is what invalidates the credential. Make
  the ordering explicit: rotate first, untrack second, rewrite optionally and
  last.
- **§19 ordering is right.** Revision 1 recommended identity first; the
  proposal's step 2 (freeze compatibility, make the baseline coherent) before
  step 3 (identity) is better, because you cannot tell whether identity work
  broke something without a green baseline. Accepted as written.

## 3. Additions required to the §20 regression matrix

§20 is strong and covers most of what revision 1 asked for. Five gaps, each
corresponding to a defect that exists today:

1. **Checkpoint wedge.** A task that registers and never reaches terminal
   status — denied at the approval dialog, tab closed, `lbp-run` failed — must
   not wedge the chain. Proven against current source: with
   `checkpoint_size=3`, three registrations then no terminal status leaves
   `window_task_count=3, checkpoint_pending=false`; `register_task` raises
   `checkpoint_required` and `continue` raises `no checkpoint is pending`. No
   escape but a new prompt or disable. §20 has no test for this class.
2. **State-transition inputs are enum-validated.** `task_status` currently
   accepts any non-empty string (verified: `totally-made-up` persists), which
   also skips the checkpoint trigger and is a second route into (1).
3. **Replay re-evaluates policy.** §20's "replays only when current recovery
   permits" is too vague to implement against. Make it explicit: a completed
   task whose server has since been removed from `servers.json`, or whose tool
   is no longer allowed, must not replay. Verified today that it does — a
   journaled result returns with an empty `servers.json` and no approval token.
4. **Browser-supplied chain/window identity is ignored.** §3 forbids accepting
   it; add the negative test. Cheap, and it is the kind of parameter that
   reappears during refactors.
5. **A conversation containing an LBP block does not become enabled.** Current
   `syncWorkflowConversation` (`content.js:59-83`) auto-sets
   `{enabled: true, active: true}` in sessionStorage whenever a chat merely
   *contains* a parseable LBP block, which then silently prepends bootstrap
   text to the user's next message. The proposal deletes this state, so the test
   is a regression guard on the deletion.

Also fold in R1's strengthened enable test (enable while scrolled up) and R4's
double-acknowledgement test (two tabs, one submission, one window increment).

## 4. Confirmed sound — leave untouched

The proposal's §21 gate and §22 non-goals are well drawn and I would not
negotiate either. Beyond those, these are correct today and re-deriving them
carries real cost:

- `ReadWriteLock` and the per-server RW barrier (`daemon.py:464-517`,
  `:1696-1745`); observe-shared / mutate-exclusive is right and the comments
  explaining it are accurate.
- `once` approval token construction and consumption (`:1311-1362`) — digest,
  session, policy-fingerprint and classification binding, consumed only after
  validation passes. §12 preserves it; keep it byte-for-byte.
- The destructive gate's *position*: first, ahead of any lease check
  (`:1180-1190`). §12 preserves this.
- `normalize_task` / `normalize_operation` rejection of model-authored
  `mutating` / `required` / `classification` (`:1402-1445`,
  `protocol.js:17-24`). §16 preserves it.
- `command_argv` shell-metacharacter fail-closed and the `argv_prefixes`
  matcher (`:849-892`) — deliberately not a shell policy language.
- Loopback binding, `valid_host`, bearer auth, CORS (`:1845-1892`),
  `atomic_write_json`, `0600` state permissions, `clip_mcp_value` and the
  `MAX_*` bounds.
- §18's decision not to split `daemon.py`. Correct — the browser is what needs
  restructuring; moving daemon internals in the same release adds risk against
  no defect.

One addition to that list: **`policy_fingerprint` should be extended to cover
the tool catalog** (`:1113-1116` currently hashes only `{server, config}`).
`tool_classification` (`:838`) reads `annotations.readOnlyHint` /
`destructiveHint` from a catalog re-fetched at preflight, so a server that
changes a tool's hints between grant and use does not invalidate a live lease.
This is not in the proposal and is a one-line change with a real invariant
behind it. `SECURITY.md:30` says the daemon derives classification; it derives
it from an input the daemon does not currently pin.

## 5. Should v0.9.2 proceed as a bounded orchestration stabilization release?

**Yes.** With R1–R10 folded in and the §20 additions written *before* code
moves, this is a legitimate freeze rather than another patch cycle.

Three things earn that answer. The proposal keeps the MCP policy/execution core
and says so explicitly (§18, §22) — that core is the part that is actually
sound. It pulls the two non-orchestration defects that make orchestration bugs
destructive rather than annoying — mutation ambiguity (§10) and journal
scoping (§8) — *inside* the release, which is exactly what revision 1 said was
required and what makes the difference between a stabilization and a
rearrangement. And §19 sequences hygiene and baseline coherence ahead of
architecture, so the work is measurable from step 2 onward.

The residual risk concentrates in R1 and R4: an enable baseline that reads
"currently visible" and a multi-tab requirement with no arbitration mechanism
are the two places where the implementation could satisfy the document and still
reproduce the live failure. Fix those two in the text before anyone writes code.

On complexity (the proposal asks not to over-build, and does not): no database,
framework, or workflow engine is warranted and none is proposed; `revision`-CAS
is not a workflow engine and is the cheapest available fix for R4. The largest
remaining simplifications are all deletions the proposal already commits to —
`chain_id` leaves the wire protocol, `CHAIN_KEY` / `WORKFLOW_KEY` / the browser
execution ledger / DOM chain reconstruction all disappear, and
`extension/chain_state.js` is deleted outright rather than ported.
