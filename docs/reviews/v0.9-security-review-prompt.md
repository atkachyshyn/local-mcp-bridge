# Independent peer review request — Local MCP Bridge v0.9 / LBP 1.2

Please perform an adversarial architecture + implementation review of this repository as the proposed **v0.9 candidate**. You have repo access. Do not assume the implementation is correct because the docs say it is.

## Context

v0.8 intentionally reduced LBP to one operation per assistant/result turn to remove an unsafe workflow-like `operations[]` mechanism. In real development that caused unnecessary model/browser turns for independent reads and validation commands.

v0.9 tries to recover efficiency without restoring mixed read/write workflows:

1. one top-level LBP operation remains;
2. new `mcp.observe` groups up to 8 independent calls on one MCP server;
3. only daemon-classified READ or VERIFY calls are legal in an observation group;
4. WRITE/DESTRUCTIVE calls remain single/exclusive;
5. a per-server writer-preferring RW barrier prevents bridge-managed writes from interleaving inside an observation phase;
6. `cargo test`-style commands may be locally classified VERIFY, which auto-runs in the default `mutations` approval mode;
7. VERIFY authority comes only from local daemon config, never model-authored classification;
8. a persistent browser status chip/panel makes bridge activity visible.

The desired user mental model is roughly:

`OBSERVE(read/verify)* -> exclusive WRITE -> OBSERVE(read/verify)* -> exclusive WRITE ...`

Do **not** recommend returning to unrestricted mixed `operations[]` unless you can demonstrate that the v0.9 constraint model is fundamentally unworkable.

## Review goals

### A. Security invariants / v0.8 non-regression

Verify that v0.9 did not regress the v0.8 fixes, especially:

- loopback-only MCP endpoints;
- bearer-token local bridge auth;
- deny-by-default allowed tools/roots/write/destructive policy;
- value-based absolute path containment including nested values, `~`, and symlink resolution;
- relative values in recognized path fields fail closed;
- model cannot author mutation/risk authority (`mutating`, `required`, `classification`);
- approvals are extension/local UI controlled and show concrete derived operation facts/arguments;
- approval tokens are validated before consumption and bound to task/session/policy/classification;
- destructive operations can remain always-explicit;
- task journal replay/idempotency and ambiguous write state handling remain conservative;
- browser auto-continue still refuses a stale assistant task if a later user message/countermand exists;
- streaming assistant messages and changed/non-empty composer state cannot be auto-submitted unsafely.

### B. `mcp.observe` safety

Try to break the claim that an observation group cannot obtain mutation authority.

Check:

- normalization in both Python and browser JS;
- max call count and unique ids;
- same-server constraint;
- whole-group preflight-before-dispatch;
- classification aggregation;
- rejection when any member is WRITE or DESTRUCTIVE;
- behavior when one READ/VERIFY member returns an MCP error or transport error;
- result correlation and task-journal replay;
- output/truncation behavior for up to 8 results;
- whether legacy LBP normalization can be used to smuggle multi-operation behavior;
- whether malformed nested objects can smuggle `classification`, `mutating`, or authority hints;
- any TOCTOU between preflight/approval and actual MCP execution that materially changes authority.

### C. RW barrier correctness

Review `ReadWriteLock` and its use, not just the smoke test.

Check for:

- write/read interleaving despite the intended barrier;
- writer starvation or reader starvation;
- deadlocks involving the per-server RW lock, MCP client lock, server-registry lock, approval lock, journal task lock, or reconnect/session recovery;
- behavior under simultaneous observation groups;
- behavior when a verification/read call blocks or times out;
- config changes/reconnects during execution;
- whether per-server scope is the right isolation unit;
- whether holding the observation side across sequential calls is sufficient to provide the documented consistency guarantee.

The implementation deliberately does **not** promise parallel MCP calls in v0.9.

### D. VERIFY trust boundary — high priority

This is the most important new attack surface.

The intended semantics are:

- VERIFY is automatic execution/validation, **not** literal read-only OS behavior;
- the tool must be base-classified WRITE by MCP and then locally matched by an explicit verification rule;
- user config is trusted authority;
- the model cannot self-classify VERIFY;
- in `mutations` mode VERIFY does not request approval;
- VERIFY is not recorded as an authoritative project mutation.

Adversarially test/reason about:

- command strings vs argv arrays;
- shell metacharacters, quoting, escaping, substitution, redirection, newlines;
- prefix matching ambiguities;
- arbitrary suffix arguments after `cargo test` / similar prefixes;
- `--manifest-path`, `--target-dir`, config-file flags, response files, toolchain selectors, cargo config overrides, test runner arguments, build scripts, custom runners, wrappers, environment behavior, and any way to turn a seemingly allowed verification command into arbitrary execution;
- cwd requirements and allowed-root containment;
- paths embedded in `--flag=value`, `key=value`, quoted config values, or other composite tokens;
- symlinks and nonexistent paths;
- URL/network arguments;
- whether the current policy should remain described as “trusted command prefix + root checks, not sandbox,” or whether a narrower rule language is required before controlled use.

Do not reject VERIFY merely because tests create `target/`; that is a known and intentional tradeoff. Instead identify whether the boundary is accurately documented and whether model-controlled arguments create unacceptable authority escalation relative to that boundary.

### E. Approval semantics

Check all four modes (`all`, `session`, `mutations`, `none`) with READ, VERIFY, WRITE, DESTRUCTIVE and an observation group whose aggregate risk is VERIFY.

Verify:

- session leases use correct risk ordering;
- a read/session lease cannot cover VERIFY/WRITE;
- a VERIFY lease cannot cover WRITE;
- policy changes invalidate leases/tokens;
- `always_approve_destructive` behaves as documented;
- observe approval, when required by `all`/`session`, covers exactly the displayed group and no changed group.

### F. Browser status UX / authority separation

Review the persistent status chip/panel for both UX and security:

- it should exist independent of task-local cards;
- it should reflect connected/offline/checking/running/approval/continuing/paused/error reasonably;
- health polling must not execute work;
- Stop chain should only stop continuation and not grant/revoke daemon authority accidentally;
- Settings should remain local UI;
- UI state must not be treated as proof that a task ran successfully;
- look for DOM races, duplicate injection, provider streaming races, reload/new-tab behavior, stale status, and overlap with existing ChatGPT controls;
- assess whether approval-required status needs a direct “Review” action in this release or can remain task-card driven.

### G. Protocol/product judgment

Please explicitly judge whether this is the right middle ground:

- old unrestricted `operations[]`: too workflow-like / unsafe;
- v0.8 one-call-per-turn: safe but chat-turn inefficient;
- v0.9 bounded `mcp.observe` READ/VERIFY group + exclusive mutations: proposed compromise.

If you disagree, propose a concrete safer/simpler alternative preserving efficient multi-read development workflows.

## Requested verdict format

Return one of:

- **READY FOR CONTROLLED USE**
- **READY WITH FOLLOW-UPS**
- **PROCEED WITH BLOCKERS**
- **DO NOT PROCEED**

Then provide:

1. **Blockers** — concrete exploitable/correctness issues required before controlled use.
2. **High-priority follow-ups** — important but not release-blocking.
3. **What you verified** — commands/probes and observed results.
4. **Security-boundary assessment** — especially VERIFY and `mcp.observe`.
5. **Protocol/product assessment** — whether v0.9 is a better tradeoff than both unrestricted arrays and single-call-only v0.8.
6. **Exact recommended patches/tests** for every blocker.

Be skeptical. A clean verdict is useful only if you actively tried to falsify the design.
