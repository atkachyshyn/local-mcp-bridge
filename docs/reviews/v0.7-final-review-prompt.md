# Final independent peer review request — Local MCP Bridge v0.7

You have repository access to **Local MCP Bridge POC v0.7**. Treat this as an adversarial final gate before controlled real-world use against local development MCP servers that may mutate source code and project files.

Do not merely confirm the architecture. Read the implementation, run the supplied tests, and write targeted repro probes where needed.

## Context

The project exists because browser ChatGPT's provider-managed MCP connector path proved intermittently unreliable even when the same local MCP server behaved correctly in MCP Inspector. The bridge keeps standard MCP locally but replaces the provider connector path with:

```text
assistant LBP task
-> browser adapter
-> authenticated loopback daemon
-> local MCP server
-> LBP result
-> browser adapter
```

An earlier independent review of v0.4 returned **PROCEED WITH BLOCKERS**. Its blockers led to deletion of the bridge-native shell/filesystem executor, daemon-owned deny-by-default tool/root/write/destructive policy, MCP-derived mutation classification, real approval UI, hardened journals/tokens, MCP client fixes, and single-operation LBP 1.1.

v0.6 then introduced configurable daemon approval boundaries (`all`, `session`, `mutations`, `none`) with ephemeral leases.

v0.7 addresses the remaining interaction problem: a browser extension cannot inject a tool result into an assistant response that is already being generated. The bridge now optionally **auto-continues across real chat turns**:

```text
human prompt
assistant -> LBP task
local MCP executes
extension -> auto-submits LBP result as next user turn
assistant continues
assistant -> next LBP task
...
```

This is explicitly documented as **turn-chained continuation, not native same-run tool calling**.

## Your goal

Decide whether v0.7 is defensible for **controlled real local development use**, including source-code mutation through a hardened local MCP server, with browser `auto_continue` optionally enabled.

Use one final verdict:

- `READY FOR CONTROLLED USE`
- `READY WITH IMPORTANT FOLLOW-UPS`
- `PROCEED WITH BLOCKERS`
- `REDESIGN`

A blocker should mean something that makes controlled source mutation or the new autonomous turn-chaining materially unsafe or unreliable, not aesthetic polish.

# Review questions

## 1. Does the architecture still make sense after auto-continuation?

Challenge whether LBP remains a justified small transport layer above MCP or whether v0.7 has accidentally become a workflow/agent protocol.

Specifically evaluate the decision to keep LBP single-operation and place auto-continuation entirely in the browser adapter rather than adding continuation/approval fields to model-authored LBP.

Is the distinction between:

- local execution authorization;
- browser result transport;
- model reasoning turns

clean and enforceable?

## 2. Verify the fundamental same-run limitation is represented honestly

Confirm the implementation/docs do not imply that a local MCP result can enter an assistant generation already in progress.

Assess whether clicking the normal provider Send button after a result is inserted is a reasonable POC mechanism for turn-to-turn continuation, and identify any semantic differences from native MCP that matter operationally (rate limits, context growth, model turn boundaries, cancellation, loss of hidden provider tool state, etc.).

## 3. Attack the auto-continue loop

This is the highest-priority new review area.

Try to cause the extension to submit something it should not.

Test/reason about at least:

- user begins typing a draft before local result arrives;
- user edits the composer after the LBP result is inserted but before Send;
- assistant is still streaming when a complete-looking LBP task block appears;
- provider Send/Stop DOM selectors change or are absent;
- two assistant LBP task messages exist in history;
- old unresolved task exists and page is reloaded;
- completed old task exists and page is reloaded;
- two task/result ids are intentionally mismatched;
- multiple LBP tasks appear in one assistant message;
- malformed task appears after a valid one;
- task execution is slow while a new assistant/user DOM update occurs;
- user presses **Stop auto-continue** at different points;
- user denies a local approval;
- user changes interaction settings mid-chain;
- user sends a new normal prompt during/after a chain;
- chain reaches the configured max round trips;
- browser tab reload resets/reuses `sessionStorage` state;
- extension/service worker reload happens between local execution and submission;
- result is `status: "unknown"` after an ambiguous mutation;
- result payload is very large/truncated;
- the normal composer already contains unrelated text from another UI action.

Determine whether the current fail-closed behavior is sufficient or whether any path can silently send user-authored/unrelated text together with a tool result.

## 4. Prompt injection under plugin-like autonomy

The model may read untrusted repository/web content and then emit an LBP task influenced by it.

Assess risk for combinations such as:

```text
auto_continue = on
approval_mode = none
broad allowed_tools
broad roots
write = true
```

The design claim is that daemon policy, not repetitive clicks, is the security boundary. Is that defensible?

Identify which configuration combinations should be explicitly warned against in UI/docs.

Do **not** simply say “prompt injection exists.” Determine whether the bridge introduces authority beyond what the user explicitly configured and whether local policy is actually enforced for every call.

## 5. Verify approval cannot be bypassed by auto-continue

Attempt to bypass:

- `approval_mode=all`;
- `approval_mode=mutations`;
- session risk tier boundaries;
- `always_approve_destructive`;
- expired/single-use approval tokens;
- policy fingerprint invalidation;
- cross-tab/browser-session lease reuse.

Make sure auto-continue affects only sending the MCP **result back to chat**, not authorization to execute the next MCP request.

## 6. Result/task correlation and replay

Review the browser-side `extractResults`/`task_id` logic and daemon journals together.

Check whether:

- an attacker/model can create a fake prior LBP result that suppresses a legitimate task;
- a completed historical task can auto-run again after reload;
- a replayed daemon result can accidentally be submitted multiple times;
- task-id collisions or conflicting task reuse remain safe;
- result correlation depends on model-controlled fields in a dangerous way.

Distinguish denial-of-execution from privilege escalation.

## 7. Browser DOM/provider coupling

Review `adapters/chatgpt.js` as a fail-closed provider adapter.

Is Send-button clicking sufficiently constrained?

Could selectors match the wrong control?

Could `findTaskHosts()` or `findResultHosts()` begin matching user/quoted/hidden content after a plausible ChatGPT DOM change?

Should auto-start require additional evidence that a task host is the most recently completed assistant turn?

If you recommend changes, keep them minimal and provider-adapter-local.

## 8. Interaction settings authority

`auto_continue`, `max_round_trips`, and payload collapsing live in `chrome.storage.local`, while execution authority lives in the daemon registry.

Is that split correct?

Could a web page, model output, or MCP server modify these settings?

Does adding the `storage` permission introduce an unexpected attack surface?

Would moving interaction preferences into daemon config materially improve security, or merely complicate the architecture?

## 9. Re-review daemon policy and MCP client

Do not assume prior fixes remained correct.

Confirm:

- loopback endpoint validation;
- bearer token handling;
- Host/sender restrictions;
- tool catalog enforcement;
- `readOnlyHint` / `destructiveHint` derivation;
- default-deny `allowed_tools`;
- write/destructive policy;
- root/path argument enforcement;
- approval token/lease binding;
- journal permissions/idempotency/ambiguous recovery;
- negotiated MCP protocol version;
- SSE response matching by JSON-RPC id;
- session pooling/DELETE/reinitialize-on-404;
- no bridge-native arbitrary executor has reappeared.

## 10. Single-operation protocol decision

Assess whether one operation per LBP assistant turn is still the right choice now that auto-continue can create multiple turns automatically.

Does this successfully avoid partial multi-operation mutation semantics, or merely move workflow complexity into the conversation?

Recommend batching only if you can show a concrete correctness/usability gain that outweighs the simpler journal/approval semantics.

## 11. User-visible truthfulness

Check that the UI accurately tells the user when:

- local call is automatic due to policy;
- approval is required;
- a session approval was granted;
- result was inserted but not sent;
- result was auto-submitted;
- auto-continue stopped/paused;
- execution state is ambiguous;
- a historical task is not auto-run.

The bridge should not make “looks like a plugin” more important than explaining exceptional states correctly.

## 12. Minimum changes before controlled use

If you find blockers, propose the **smallest** patch set that closes them. Prefer deletion/fail-closed behavior over building a general browser automation framework.

Classify every finding as:

- `BLOCKER`
- `IMPORTANT`
- `POC ACCEPTABLE`

For every blocker, state:

1. exact file/function;
2. concrete failure/attack sequence;
3. whether you reproduced it;
4. minimal required fix.

# Explicit non-goals: do not recommend these without a concrete blocker

Do not expand scope into:

- workflow DAGs;
- multi-operation LBP batches;
- remote/non-loopback MCP;
- stdio server spawning;
- browser-provider private APIs;
- autonomous background polling/watchers;
- credential delegation;
- a second provider adapter;
- native-host packaging;
- a custom local LLM orchestrator;
- replacing MCP itself.

The question is whether this **small bridge** is ready for controlled use, not how to turn it into an agent platform.

# Final output format

Start with the verdict and a short executive summary.

Then provide:

1. **Blockers**
2. **Important follow-ups**
3. **Acceptable POC shortcuts**
4. **Auto-continue attack/repro results**
5. **Security boundary assessment**
6. **Protocol/architecture assessment**
7. **Minimum patch list, if any**
8. **What not to build yet**

Be skeptical. If the implementation is ready, say so. If it is not, identify concrete defects rather than theoretical discomfort.
